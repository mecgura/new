# Phase 12 — Notification Center

One place where every user sees what needs them, driven by one engine, with external delivery to patients delegated to Phase 11.

```
business event → event hub (notifications/events.ts)
   ├─ in-app:  rule → recipients → preferences → idempotency → quiet hours → grouping → Notification row
   └─ patient: Phase 11 communication engine (WhatsApp / SMS / email) — channels narrowed by the clinic's rule
```

## What exists
* **Model** — the existing `Notification` table was extended (not duplicated): `category`, `priority`, `actionUrl`, `patientId`, `archivedAt`, `expiresAt`, `visibleAt` (quiet hours), `ackRequired/acknowledgedAt/By`, `escalatedAt`, `sourceEventId`, `groupKey/groupCount`, `metadata`, `updatedAt`; `tenantId` is nullable for platform alerts. New: `NotificationEvent` (idempotency ledger), `NotificationRule`, `NotificationPreference`, `NotificationUserSettings`, `NotificationSettings`. Migration `20261013090000_phase12_notifications` (SQLite + PostgreSQL; the old rows are kept). Status is derived: UNREAD / READ / ARCHIVED / EXPIRED.
* **Catalogue** (`src/lib/notifications/catalog.ts`) — 40 kinds in 10 categories with default audience, priority (LOW → CRITICAL), acknowledgement and where "Open" leads. Priority rules: an admin can set up to URGENT; CRITICAL belongs to security/system incidents the system raises itself; security notices can't be switched off or lowered.
* **Engine** (`engine.ts`) — never trusts a recipient, tenant or patient id from the browser: recipients come from the event's entity (`@doctor` = that case's doctor, `@assignee`, `@self`, `@patient` = that patient's portal login, or role keys). The person who did the action is not told about it. Per recipient: user's category switch (security/urgent exempt) → ledger (same event never twice, even in parallel, even after grouping/archiving) → quiet hours (low/normal wait; high+ never) → grouping (OPD check-ins fold into "N patients have checked in"; never security/urgent/acknowledge-required) → row. Titles/messages are built from templates with cleaned values (control characters stripped, 200-char cap); React renders them as text; action URLs must be in-app paths.
* **Event hub** (`events.ts`) — the business modules call this instead of Phase 11 directly; it does the in-app notifications and calls the Phase 11 trigger for the patient's phone/inbox. Hooks (after the business commit; never able to fail it): appointments (requested/confirmed/rescheduled/cancelled/no-show/reminder), OPD (check-in grouped, emergency, called, completed), patient registered, patient portal request, prescription (patient + pharmacy), lab (ordered, sample collected/rejected, report released/amended), follow-up (assigned, reminder, overdue digest), billing (bill issued, payment, refund requested, overdue digest), pharmacy (low/out of stock, expiring/expired batches, purchase received), security (account locked, role changed, portal password/sessions/reset), system (messaging provider problems, scheduler stale, queue backlog, escalations), personal daily digest (opt-in).
* **Scheduler** — no second scheduler: `runNotificationJobs()` runs on the Phase 11 tick (`/api/internal/communications/run`): patient in-app reminders (work with every external channel off), follow-up/billing digests, pharmacy stock & expiry from real inventory (once a day per kind), provider-failure alerts, escalation (once, only if the rule has `escalateAfterMin`), retention (off by default; archives read, non-security, non-critical, acknowledged items; nothing is ever deleted), digests. Super Admin health checks also run lazily when a Super Admin polls.
* **Phase 11 integration** — the clinic's rule can restrict which external channels a patient message may use (`externalChannels`); Phase 11 honours it (`notifications/policy.ts`) on top of consent, provider and channel settings. Notification detail shows the **actual** Phase 11 delivery status (staff: real status; patient: Sent / Delivered / Not delivered, no provider details). Fallback stays in Phase 11.

## Screens and APIs
Bell in the header (all roles incl. Super Admin): unread badge (99+), accessible name with counts, dropdown with the latest 8, mark all read, Escape closes, fits phones. `/notifications` — filters (All / Unread / Needs acknowledgement / Archived / Expired), categories, priority, date (today / yesterday / 7 d / 30 d / custom), server-side search (title, message, entity id; patient name only for people allowed to see patients), pagination, mark read/all, archive/restore/archive-read, acknowledge, detail panel (desktop) or sheet (mobile), "Today" numbers from real queries. `/notifications/settings` — categories, quiet hours, daily summary. `/settings/notifications` — rules (audience, priority, acknowledge, escalation minutes, patient channels) and retention (needs `notifications.configure`, clinic admin only). `/platform/notifications` — Super Admin: system/security alerts across clinics with clinic/category/severity/status/date filters, failed-message and provider-failure signals; never patient content. Portal: `/portal/notifications` uses the same centre (patient categories, archive, read) plus the Phase 11 message list.
APIs: `GET /api/notifications` (+`/unread-count`, `/summary`, `/[id]`, `PATCH /[id]/read`, `PATCH /[id]/archive`, `POST /[id]/acknowledge`, `POST /mark-all-read`, `POST /archive-read`, `GET|PATCH /preferences`, `GET|PUT|DELETE /rules`, `PUT /settings`), the same under `/api/patient/notifications`, `GET /api/platform/notifications`. Each derives user and clinic from the session; patients cannot use the staff endpoints and vice versa.

## Security
Own-notifications-only queries (`userId` + `tenantId` from the session), quiet-hours/expired/archived handled in the query, action links re-checked at open (role permission for that record type + the record exists in the viewer's clinic + in-app path only), rate-limited bulk actions, audit of high-priority creation, acknowledgement, bulk actions, escalation, rule/preference/retention changes (ids and counts only — no message text).

## Not built / limits
* **Not real-time**: the bell polls every 30 s (and on focus); the centre refreshes every minute. There is no websocket/SSE channel in this project, and nothing claims otherwise.
* Staff notifications are **in-app only**: Phase 11 delivers to patients, not staff. Staff WhatsApp/SMS/email is not built.
* Unwired kinds (catalogued, no source event yet): staff password change (there is no staff change-password flow), new sign-in (off by default, no hook), consultation-started, patient-document-uploaded (no upload store), payment-failed/refunded to the patient, token-approaching, backup warning, maintenance notices.
* Existing lab/follow-up digest reminders (lazy, per user) still exist and now appear in the same centre.
* Admin-configurable audiences are role keys / `@doctor` / `@assignee`; per-user recipient lists are not.
